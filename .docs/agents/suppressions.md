# Warning suppressions

How to add a suppression of a compiler, analyzer or linter diagnostic. Linters count as analyzers here. The forms:

- .NET: `<NoWarn>`, `#pragma warning disable`, `#nullable disable`, `[SuppressMessage]`, an `.editorconfig` severity of `none`, `silent` or `suggestion`.
- Web: an inline `oxlint-disable*` or `eslint-disable*` comment (oxlint honors both), or a rule turned off in `frontend/.oxlintrc.json`.

`SuppressionArchitectureTests` fails on any of these that has no `issue #<n>` on its line or the line above.

A suppression is a hard gate: fix the code instead wherever you can.

## Steps

1. **Get per-instance approval.** Present each suppression to the user on its own: the code, its location, the form, the **justification** (why the code can't be changed instead, e.g. "the third-party package emits this on every `DateTime` field and we can't change the library") and the **consequence** (what signal is lost, who is affected, and whether it is scoped to one project or global, e.g. "NU1903 will no longer surface, so a newly-introduced vulnerable package will not be visible in `dotnet build` or CI"). Wait for an explicit "yes" to that specific suppression. Approval is never inferred: not from an earlier approval, even of the same code under the same justification, and not from a "same condition as #N" note. If the user approves only some of N, go on with those only.
2. **Get a separate approval for the issue.** Filing the tracker record is a second acceptance: approving the record is not approving the suppression, and vice versa.
3. **File one issue per instance**: a specific code in a specific file on a specific line, labelled `suppressions`. There is no shared registry issue; the per-instance issue is the cleanup reminder. Its body records the approver's GitHub username, their acceptance verbatim, the date, the justification, the consequence and scope, the "cleanup when" condition, and a link to the file.
4. **Write it at the narrowest scope.** A `<NoWarn>` in one `csproj` beats one in `Directory.Build.props`; a `#pragma warning disable` around one line beats a file-level `#pragma`.
5. **Cross-reference it** on its line or the line above, naming the code, the approver and the issue: `// NoWarn MSTEST0001 - approved by @<user>, issue #<n>: <one-line justification>`.
6. **Close the issue** when the suppression is removed from the codebase.

## Excluded

Auto-generated code: any file under a `Migrations/` directory, or carrying the `// <auto-generated />` banner. Its suppressions are emitted by a tool (the EF Core migration generator, design-time tooling) and regenerated wholesale. Leave them as generated and file no issue for them.
